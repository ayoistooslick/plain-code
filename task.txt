Implement Plain v2.1.1.

This release is a corrective/stabilization release after v2.1.0.

The goal is NOT to add another AI compilation layer. The goal is to make the deterministic compiler itself capable of handling the backend features we previously attempted through Complex Compilation, while fixing the real runtime issues discovered through testing.

IMPORTANT ARCHITECTURAL DECISION:

DELETE COMPLEX COMPILATION COMPLETELY.

Treat it as if it never existed.

Do not replace it with another AI fallback.
Do not add more AI compiler rules.
Do not make unsupported Plain syntax silently enter an AI compiler.

Plain must have ONE authoritative deterministic compiler.

If syntax is unsupported, `plain check` must give a deterministic compiler error explaining exactly what is wrong and, where practical, showing the expected syntax.

Do not guess syntax during implementation or testing. Every new language feature must have one explicit, documented, deterministic syntax.

==================================================
PART 1 — REMOVE COMPLEX COMPILATION
==================================================

Remove the entire Complex Compilation pipeline:

- AI compilation fallback
- fallback invocation from deterministic compilation
- compiler/rules dependency that only existed for Complex Compilation
- AI compilation error paths
- "trying Complex Compilation" messages
- dead configuration
- dead resolver/rule code
- tests that only verify AI fallback behavior

`plain run` should behave as:

deterministic compile
        ↓
success → generate/run
failure → precise compiler error

There must be no second compiler.

Do not break the existing deterministic compiler.

==================================================
PART 2 — MOVE THE USEFUL COMPLEX-COMPILATION CAPABILITIES INTO THE DETERMINISTIC COMPILER
==================================================

The features we previously needed Complex Compilation to handle must become proper deterministic compiler capabilities.

Inspect the existing compiler architecture first.

Do not invent syntax based on JavaScript.
Do not invent syntax based on English guesses.
Follow existing Plain conventions and extend them consistently.

The language must have explicit grammar/AST/compiler support for the capabilities necessary to build real backends.

At minimum, make the deterministic compiler capable of:

- robust variables
- reassignment
- strings
- numbers
- booleans
- null
- arrays
- objects
- nested objects
- nested arrays
- property access
- array indexing

- loops

- arithmetic

- string operations
- array operations
- JSON construction
- JSON parsing/serialization
- async operations

- reusable application logic

Preserve existing valid syntax.

IMPORTANT:
Use the ACTUAL existing Plain grammar as the source of truth.

For example, if Plain currently uses:

{ id: 1, name: "Manchester City" }

then that is the syntax.

Do NOT change it to:

Do not invent syntax merely because it looks natural.

Every newly supported construct must have:

- runtime generation
- compiler diagnostics
- tests
- documentation

==================================================
PART 3 — `use` MUST BE A REAL DEPENDENCY FEATURE
==================================================

Keep and strengthen the v2.0.1/v2.1.0 `use` system.

Plain must support explicit dependency declarations such as:

use "express"
use "express" as exp
use "tesseract.js" as tssc
use "@ayoxx/plain-code"
use "some-package@^2.0.0"

Requirements:

- validate package names
- support scoped packages
- support aliases
- support versions/version ranges
- resolve/install dependencies deterministically
- distinguish built-in Node modules from npm packages
- support CommonJS packages
- support ESM packages where practical
- expose imported dependencies to generated/runtime code
- allow aliases to actually be used
- produce deterministic errors for invalid dependencies

`use` must not merely install packages.

If a programmer writes:

use "express" as exp

the `exp` binding must genuinely exist and be usable by Plain's supported dependency-interoperability mechanism.

PART 7 — DATABASE BUG AND ARCHITECTURE
==================================================

Fix the v2.1.0 database capability exposed by the real Termux test.

The Plain program compiled successfully and deterministically:

- database syntax was recognized
- better-sqlite3 was resolved/installed
- Express was resolved/installed
- runtime dependencies passed
- JavaScript was generated

But execution failed because better-sqlite3's native binding was unavailable:

Cannot find module .../better-sqlite3/build/Release/better_sqlite3.node

This is a runtime/dependency portability problem, not a Plain syntax problem.

Investigate the existing database implementation and make the database capability genuinely portable and production-usable.

Requirements:

1. Do NOT remove or weaken Plain's deterministic database syntax.

2. Do NOT make Complex Compilation responsible for database programs.

3. Do NOT simply tell users to manually install better-sqlite3.

4. Separate Plain's database abstraction from one hardcoded native SQLite implementation.

5. Determine what database backends are realistically usable across:
   - Linux x64
   - Linux ARM64
   - Termux/Android ARM64
   - Windows
   - macOS

6. For SQLite, investigate a portable implementation where possible, including WASM/pure-JS options or another runtime that does not require an unavailable native `.node` binary on Android.

7. If multiple database drivers are supported, make the backend selectable without changing high-level Plain database semantics.

8. Preserve:

database "..."

query

insert

execute

transaction

parameterized queries

result handling

existing SQL behavior

9. Database support must handle real applications, not toy examples.

10. Add runtime capability detection.

11. If a backend genuinely cannot run on a platform, produce a clear deterministic diagnostic.

12. Add deterministic compiler tests.

13. Add actual runtime integration tests.

14. Add a Termux/Android-compatible database test if the environment permits it.

The test must EXECUTE a database operation. Installing an npm package is not enough.

15. Test:

HTTP route
→ database query
→ JSON response

16. Do not break existing v2.1.0 database programs.

17. Investigate why the dependency installer reported:

"✓ better-sqlite3 installed"

while the native runtime binding was unavailable.

Plain must distinguish:

package downloaded

from:

runtime dependency installed and usable.

18. After fixing the implementation, rerun the football backend test.
