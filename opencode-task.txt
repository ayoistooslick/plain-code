PLAIN CODE v2.0.0-LATEST PRE-RELEASE FIX

We have now tested the hosted compiler extensively. Do NOT merely patch the individual generated examples. Fix the underlying compiler architecture while preserving the explicit rule-based language design.

IMPORTANT LANGUAGE PRINCIPLE

Plain is NOT an English prompt language.

Complex Compilation is an internal compiler capability that translates valid Plain syntax covered by explicit compiler rules into JavaScript.

Never make the resolver accept arbitrary English because an AI model can understand it.

If no explicit rule covers the source, compilation MUST fail with the existing "no rule covers this source" behavior.

Every new Plain feature must have an explicit rule defining:
- syntax
- semantic meaning
- JavaScript target
- dependencies
- async behavior
- invalid forms
- security considerations
- resolver triggers
- tests

The AI may perform complex translation inside those boundaries, but it must never invent language semantics from arbitrary natural language.

CURRENT TEST RESULTS

These work correctly:
- HTTP fetch
- multiple fetches
- POST fetch with headers/body
- REST API routes
- REST + fetch
- WebSocket
- Telegram using the current documented syntax
- Cron standalone
- Email standalone
- Email verification
- arbitrary English is correctly rejected

These are BROKEN:

1. Cron + Fetch

Input:

schedule task "* * * * *" as
    remember response as await fetch "https://jsonplaceholder.typicode.com/todos/1"
    if response is ok
        remember data as await response.json()
        show data
    done
done

Current compiler incorrectly selects http/fetch and outputs only the fetch body.

The cron schedule is lost.

2. Cron + Email

Input:

remember transport as email transport with
    host is "smtp.example.com"
    port is 587
    secure is false
    auth user is env("SMTP_USER")
    auth pass is env("SMTP_PASS")
done

schedule task "0 9 * * *" as
    send email via transport
        to is "test@example.com"
        subject is "Daily Plain report"
        text is "The scheduled task ran successfully."
    done
done

Current compiler incorrectly selects communication/email and outputs an immediately-executed sendMail() instead of placing it inside cron.schedule().

3. REST + Cron + Fetch

Input:

remember app as express app

app get "/health" as
    reply "ok"
done

schedule task "*/5 * * * *" as
    remember response as await fetch "https://jsonplaceholder.typicode.com/todos/1"
    if response is ok
        remember todo as await response.json()
        show todo
    done
done

listen app on port 3000

Current output contains:

schedule("*/5 * * * *", async () => { ... });

but:
- no node-cron import
- dependencies only contain express
- the cron implementation is therefore invalid

This MUST be fixed.

4. Cron shorthand

The cron.md documentation explicitly declares this valid:

every 5 minutes as
    show "Heartbeat"
done

But cron.json does not contain a resolver trigger that matches this syntax.

The resolver currently rejects it as "no rule covers this source".

Fix the metadata/resolver trigger so documented syntax and resolver behavior agree.

ARCHITECTURAL REQUIREMENT

DO NOT solve the above by adding special-case prompts such as:

"If source contains schedule task, tell the AI to also use cron."

That would be fragile and would make the rule system progressively worse.

The compiler must understand that a Plain program can contain multiple rule-defined capabilities.

A source program may legitimately combine rules.

Examples:

- REST + HTTP fetch
- REST + Cron
- Cron + HTTP fetch
- Cron + Email
- Telegram + HTTP fetch
- Telegram + Database
- WebSocket + REST
- Cron + Email + HTTP fetch
- REST + Database + Authentication

The resolver/compilation architecture must preserve ALL applicable semantics.

RULE COMPOSITION

Investigate the existing resolver, AI client, validator, rule loader, and compilation pipeline.

Determine whether the current architecture assumes exactly ONE selected rule.

If it does, refactor it safely so a complex source can resolve against multiple compatible rules or against a composite rule context.

Do NOT break deterministic compilation.

The existing deterministic compiler must remain authoritative for syntax/features it already handles.

Complex Compilation should only handle source that reaches the AI compilation path according to the existing architecture.

The final generated JavaScript must preserve every capability represented in the source.

DEPENDENCY CORRECTNESS

The final compiler result MUST contain every runtime dependency required by the generated JavaScript.

Examples:

Cron alone:
dependencies must contain node-cron

Email alone:
dependencies must contain nodemailer

Cron + Email:
dependencies must contain both:
- node-cron
- nodemailer

REST + Cron:
dependencies must contain both:
- express
- node-cron

REST + Cron + Fetch:
dependencies must contain:
- express
- node-cron

If fetch uses only the Node runtime/global fetch available by the compiler's target environment, do not invent a package dependency.

Generated imports/requires must agree with dependencies.

There must never be generated identifiers such as:
schedule(...)
cron.schedule(...)
WebSocketServer
nodemailer
express
etc.
without the corresponding required import/dependency when the target runtime requires one.

ASYNC CORRECTNESS

Preserve the existing async validation architecture.

If compiler output says:

async: true

validation must validate the generated JavaScript in the same async execution context used at runtime.

Do not regress the existing top-level-await fix.

For nested async constructs:
- async route handlers must remain async
- async cron callbacks must remain async
- async Telegram handlers must remain async according to their rule
- async email operations must be awaited
- async fetch operations must be awaited

Do not mark the whole program async unnecessarily if the generated target does not require it, but do not lie in the output contract.

RULE SELECTION

A rule should not "win" merely because it contains one matching phrase.

For a source containing multiple capabilities, the compiler must account for all applicable rules.

For example:

REST + fetch must not cause the REST semantics to disappear.

Cron + fetch must not cause the cron semantics to disappear.

Cron + email must not cause the schedule to disappear.

REST + cron + fetch must preserve all three.

If the current AI architecture sends the selected rule and source to the provider, redesign that context so the provider receives the relevant rule specifications together with their constraints.

The AI must be explicitly instructed that:
- it may only use syntax/semantics defined by the supplied rules
- it must preserve all applicable constructs
- it must not invent unsupported Plain syntax
- it must not remove a construct merely because another rule also matches
- it must produce valid JavaScript satisfying all selected rule contracts
