IMPORTANT PRODUCT DIRECTION

Plain is an Intent-Oriented Programming Language (IOPL).

It is NOT an English-to-code system.
It is NOT a prompt language.
It is NOT a chatbot that accepts arbitrary natural-language instructions and guesses what the programmer meant.

Humans may write readable, sentence-like Plain syntax, but Plain still has a defined language, defined constructs, defined semantics, and defined rules.

The compiler must therefore remain strict.

We are introducing/reframing the v2.0.0 internal compilation architecture as:

Complex Compilation

Do NOT publicly brand this as "AI-assisted programming", "AI coding", "natural-language programming", "prompt-to-code", or anything that suggests Plain accepts arbitrary English.

The model/provider is an implementation mechanism used by the compiler when a defined Plain capability is too complex to hard-code into the deterministic compiler.

Think of the architecture like this:

Plain source
→ Plain language/rule recognition
→ deterministic compiler OR Complex Compilation
→ validated JavaScript
→ normal bundler/runtime

The important distinction:

The rule defines what Plain means. The compiler/model implements that meaning.

The model must NEVER be allowed to invent language semantics.

2. COMPLEX COMPILATION MUST REMAIN RULE-BOUND

This is the most important requirement.

Current and future Complex Compilation must only activate when the source matches a defined, versioned Plain rule.

Do NOT create a fallback like:

«"If the deterministic compiler cannot understand the sentence, send the sentence to the model and let it figure out what the user wants."»

That would turn Plain into a prompt language.

Instead:

1. Lexer/parser/deterministic compiler attempts normal compilation.
2. If a construct is unsupported, the rule resolver determines whether a known Plain rule matches it.
3. Only a matching rule may invoke Complex Compilation.
4. The rule defines:
   - syntax
   - semantics
   - valid forms
   - invalid forms
   - JavaScript target
   - dependencies
   - async requirements
   - security constraints
   - examples
5. The model translates the defined construct according to the rule.
6. Generated JavaScript is validated.
7. Dependency/import requirements are validated.
8. The normal bundler/runtime executes the result.

If no rule matches, Plain must reject the construct.

It must NOT say:

«"Sure, I'll interpret that."»

It should produce a useful compiler error explaining that the requested construct is not part of the current Plain language/rule set.

This is essential for language integrity.

15. DO NOT BREAK THE DETERMINISTIC COMPILER

This is critical.

The deterministic compiler remains authoritative.

Do NOT move existing deterministic language features into Complex Compilation unnecessarily.

Do NOT make normal Plain syntax dependent on a remote service.

A deterministic Plain program should continue to compile:

- offline
- without provider credentials
- without network access
- without Complex Compilation

Complex Compilation is an extension, not the foundation.

16. DO NOT CHANGE PUBLIC SYNTAX CASUALLY

Before introducing new syntax:

1. inspect existing grammar
2. inspect parser
3. inspect lexer
4. inspect generator
5. inspect existing rules
6. check for collisions
7. define the syntax in documentation
8. add tests
9. only then implement it

Do not introduce "natural language" variations just because they sound nice.

Plain can be readable without being ambiguous.

For example, a human saying:

«"I want to eat you"»

must not be interpreted as a programming instruction merely because an AI model could guess some intended meaning.

The compiler needs recognizable Plain constructs.

This is exactly why the rule system exists.

CORE PRINCIPLE

Never optimize Plain for:

«"The AI can probably figure out what the user means."»

Optimize Plain for:

«"The language precisely defines what this construct means, and Complex Compilation can implement that construct without requiring the deterministic compiler to contain thousands of lines of specialized implementation code."»

That distinction is the foundation of Plain v2.0.0.

Complex Compilation should make Plain more capable, not less of a programming language.
